# Architecture Diagrams

- Start from authoritative architecture text, code, configuration, or an explicitly labeled proposal. Never invent ownership, dependencies, or trust boundaries to make a diagram complete.
- Give each diagram one purpose, audience, abstraction level, and system boundary. Split views when one canvas mixes context, containers, components, sequences, deployment, data, or risk at unreadable scale.
- Include only components and external actors needed for that purpose. Show ownership, trust, runtime, data, or lifecycle boundaries when they affect interpretation.
- Make relationships directional and label their meaning or protocol only when known. Remove decorative edges; group repeated paths and avoid crossings where possible.
- Use a clear reading axis, aligned blocks, restrained color, high contrast, short labels, and a legend only when notation is not obvious.
- Use the requested format. Otherwise prefer Mermaid for a simple text-maintained view and use DrawIO, Excalidraw, or an available visualization tool when layout or presentation needs justify it.
- Validate the delivered syntax or file and compare every material node, boundary, and edge with its source. Mark inferred, optional, future, and deferred elements explicitly.
- Deliver the artifact plus a one-sentence purpose and only the assumptions needed to interpret it. Do not surround a self-explanatory diagram with an essay.

Stop before drawing when contradictory sources or a missing ownership decision would force a misleading edge or boundary.
